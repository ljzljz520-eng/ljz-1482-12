# 协作方案选型：OT / CRDT / 显式版本合并

ScriptEditor 的"拆场"是**结构性操作**（场次树里移动一批有身份的节点，且字幕锚点、素材区间要跟随或进入待修复），不是纯文本编辑。三种方案对比：

| 维度 | OT（操作变换） | CRDT（协同数据结构） | ✅ 版本化修订 + 显式三路合并（本项目） |
|---|---|---|---|
| 核心机制 | 操作对彼此做 transform 函数后重放 | 无冲突数据类型（RGA/OR-Set 等），靠代数性质收敛 | 每个操作带 `baseSeq`；服务端线性化为仅追加 Revision；后到操作在新快照上按**稳定身份**重放，语义不能自动合并就产出**显式冲突** |
| 对结构操作（拆/合/删场） | transform 规则数量随操作类型平方增长；"把元素从已被删除的场里拆出来"没有自然的变换结果，通常只能退化成冲突或丢操作 | 树/列表 CRDT 可以收敛，但**收敛 ≠ 语义正确**：两个节点身份可能合并出一个谁都没预期的场；锚点引用的意图无法靠数据类型自动表达 | 身份缺失/源场已删直接判定为 `split_vs_delete` 等结构冲突，原操作完整落库，由人在"待修复"面板显式选择（恢复原场再拆 / 抢救为待归场 / 放弃并留痕） |
| 可审计 / 撤销 | 变换后的操作与用户意图不再一一对应，难以解释"我撤销的到底是什么" | 墓碑与 op 膨胀；"只撤销本人意图、不抹掉他人后来修改"需要额外因果层 | Revision 是不可变证据链（作者、baseSeq、触碰身份、操作前指纹、inverse、rebase 轨迹）；undo 是带 ownership + 指纹校验的新修订 |
| 引用完整性（锚点/素材区间） | 需在每个 transform 分支里维护，极易漏 | 最终一致窗口内会出现悬空引用 | 服务端每次提交在 Serializable 事务内跑 `validate()`；元素删除把锚点置 `broken`、区间置 `review`，从不级联删除、不悬空 |
| 实现与运维 | 需复杂 transform 矩阵 | 需嵌入 CRDT 库并处理墓碑回收、快照压缩 | 一条修订表 + 纯函数引擎，规则可测（26 个用例），PostgreSQL 事务即可保证线性化 |
| 离线 | 可支持，但重连变换复杂 | 天然支持 | 离线操作进本地队列（明确 local-only）；重连按 opId 幂等提交，服务端 rebase 或显式冲突 |

## 选定方案与支持边界

**选定：版本化事件溯源 + 显式三路合并。** 操作在服务端被赋予全局单调 `seq`；客户端快照带修订号，所有编辑表达为"基于某修订的意图（Op）"。

### 能自动合并的情况
- 不同实体（不同场次/元素）的编辑互不影响，直接在新 head 上重放（记录 `rebasedFrom/rebasedOnto`）。
- 同一字段、两人改成相同值：殊途同归，无冲突。
- 新场插入用 `orderIdx` 插值（前后场 orderIdx 均值），不重排任何 id。

### 必须显式裁决的边界（拒绝"猜"）
1. **字段三方不一致**：我的基线值、我的新值、云端现值互不相同 → 字段冲突，展示三值供选择/手填。
2. **甲拆场、乙删除原场**（`split_vs_delete`）：拆出的元素绝不静默消失——可"恢复原场并完成拆场"或"原场维持删除、元素抢救为待归场"。
3. **合场的任一方被删**（`merge_vs_delete`）、**删场时他人刚编辑过场内元素**（`delete_vs_edit`）：同样显式处理。
4. **跨拆分边界的素材区间**：不自动裁剪（裁哪里属于创作判断），置 `review` 待人工确认。

### 撤销的边界
撤销本身是一条 `restoreState` 修订，受三重约束：
- 只能撤销**本人**创建的修订；
- 目标修订触碰的身份若被**他人后续修订**改过（指纹比对失败），硬阻止——防止"我撤销时把别人刚改的台词一并抹掉"；
- 本人后续又改过：允许撤销但二次确认并在结果中给出 warning。

### 刻意不做的事
- 不做"光标级实时"的字符级合并：脚本场域以短句/镜头为最小单位，字段级锁粒度足够且结果可解释。
- 冲突不做自动定时解决、不做"后写覆盖（LWW）"：所有裁决都必须留下人的选择记录（MergeConflict.resolution + 新 Revision）。
